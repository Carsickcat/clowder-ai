# AI for Operations：产品原子能力、SRE 工作流与收益验证调研

研究日期：2026-07-14  
研究目的：补足上一版趋势型研究的产品与工作流层。回答的不是“哪些厂商做了 AI 运维”，而是 AI 运维产品实际上由哪些可组合能力构成、SRE 在何时以何种界面使用它、以及哪些收益能够被合理归因。

## 核心问题

1. 将下列产品按同一原子能力模型拆解：Gemini Cloud Assist investigations、Amazon CloudWatch investigations、Azure Copilot Observability Agent、Dynatrace Assist、HolmesGPT、K8sGPT、Robusta、Botkube、AIOpsLab。
2. 对每个产品分别说明：触发方式、上下文汇集、推理/调查循环、证据与输出、可调用工具或变更边界、身份权限、反馈/记忆/评估。
3. 将能力映射至四类 SRE 用户场景：告警当下的 on-call、跨团队事故协作、平台/值班负责人配置与治理、复盘与演练。
4. 比较六种交互方式：告警自动触发、当前控制台上下文入口、自由对话、事件线程/ChatOps、定时后台巡检、工单/PR 交接。
5. 对“为 SRE 带来的收益”做证据分级：
   - 可直接从一手产品文档确认的工作流变化；
   - 可用团队自身基线度量的领先指标；
   - 不能仅靠厂商材料证明的 MTTR、成本或人力因果结论。
6. 归纳安全与治理边界：遥测提示注入、只读与写权限分离、可审计证据链、runbook 受控执行、预览功能与成本风险。

## 证据与写作规则

- 厂商功能仅引用官方文档；开源项目以源码仓库/官方文档为准；安全和评估结论追论文或原始实验。
- 搜索结果只作为线索，逐条打开一手来源。记录 claim ledger，标记 use / use-with-caveat / reject。
- 不引用厂商未给出可复核基线的 ROI、降噪率或 MTTR 百分比；不能证明的地方明确写“尚不能归因”。
- 明确标示 Preview、版本、许可边界和适用范围，避免把单一平台的产品能力泛化为行业结论。
- 最终产物以产品能力图谱、用户旅程、交互模式比较、收益度量框架、选型/试点建议为主，而非工具清单。
