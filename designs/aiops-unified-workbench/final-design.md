# NOVA Ops V2 设计说明

## 核心判断

统一运维不是把五个模块塞进同一个调查页，而是让它们共享同一业务上下文和证据链，同时各自完成不同专业判断。产品主入口因此从“模块导航”改为“角色与场景”，模块作为旅程中的专业工作面和可深链入口。

## 信息架构

```text
场景首页
├─ 八项原子能力：Observe → Contextualize → Detect → Correlate
│                  → Investigate → Decide → Act → Verify & Learn
├─ 发布后验证（发布负责人）
├─ 告警风暴处置（值班 SRE）
└─ 关键服务日巡（服务 Owner）

进入任一旅程
├─ 左：角色任务、决策问题、五步旅程
├─ 中：当前步骤的专业工作面
├─ 右：事实 / 假设 / 缺口 / 建议及人工 verdict
└─ 顶：锁定 service / env / time / change
```

## 五个专业页面

| 模块 | 页面骨架 | 核心动作 |
|---|---|---|
| 监控 | SLO KPI、发布前后/基线/对照曲线、服务拓扑 | 比较组、选择异常节点、确认影响 |
| 告警 | Raw → Correlated → Primary Event、告警簇、业务影响、路由 | 接纳归并、拆分噪声、确认 Owner |
| 日志 | Query、Pattern Clusters、Facet Inspector、原始样本 | 聚焦模式、比较维度、钉入证据 |
| 巡检 | 覆盖环、检查定义、Run 历史、Finding 闭环 | 审核候选、运行、分派、复验 |
| 拨测 | 地域/设备、用户步骤、Waterfall | 对照地域、定位失败步骤、验证恢复 |

## 用户旅程结果

每条旅程必须以人工决策结束，并产出：

- 可点击证据包；
- Owner 与责任边界；
- 受控动作或治理报告；
- 复验门槛；
- 本次流程内可核算的跳转次数、结论耗时与证据覆盖。

## 竞品工作流取舍

- 采纳 Datadog 的多入口调查与 `inconclusive`；不展示完整 Agent Trace。
- 采纳 AWS 的 Observation/Hypothesis 人工接纳、调查时间线与报告。
- 采纳 Google 的来源回链、多假设与 revision 思路。
- 保留本产品更严格的 `unknown`、数据新鲜度、覆盖与基线可比性门禁。

## 视觉方向

深色运维工作台并非“大屏炫技”，而是用低干扰背景、窄语义色和高密度结构承载证据。三个场景使用不同 accent，但共享 token；五模块差异来自信息结构与交互，不依赖换色。
