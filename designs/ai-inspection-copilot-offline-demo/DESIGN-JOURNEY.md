# 双入口巡检工作台 · 高保真设计规格

设计：烁烁 ｜ 实现：丢丢 ｜ 检视：山本
输入：co-creator 用户旅程（首访对话生成 + 复访历史直跑）；丢丢数据契约（InspectionDraft / SavedInspectionDefinition / InspectionRun）
纪律继承：DESIGN-SIMPLIFY 六条文案纪律全文有效——本轮是加能力，不是加口号。

## ① 核心设计立场

**我正式修正自己上一版的边界。** 我曾立"方案是加速器，不是入口"，针对的是*团队审批 Playbook*；co-creator 的旅程说得对——*个人保存的巡检任务*必须是入口，而且是复访用户的第一屏。两件事不冲突，分层解决：

- **个人保存任务**（我自己的巡检）→ 首页可见、一键直跑、立即可用，无审批。
- **团队 Playbook**（要给别人用的）→ 仍走审批与匹配卡，治理层，不抢入口。

首访与复访共用同一个工作台骨架：**右侧常驻对话框 + 主区任务面板**。对话是发动机，不是装饰。

## ② 信息架构：一个工作台，两条入口

```text
┌─────────────────────────────────────────────────┬──────────────┐
│ NOVA 巡检工作台                        [离线演示] │              │
├─────────────────────────────────────────────────┤  对话框       │
│ 已保存巡检（复访第一视觉区）                      │ （常驻）      │
│ ┌─────────────────────────┐                     │ ┌──────────┐ │
│ │ 支付配置变更巡检    [直跑▶]│ ← 卡片=名字+上次状态+时间│ │ 对话记录  │ │
│ │ 上次：Pause · 2 小时前   │                     │ │          │ │
│ ├─────────────────────────┤                     │ ├──────────┤ │
│ │ 订单发布后验证      [直跑▶]│                     │ │ 输入框    │ │
│ │ 上次：Proceed · 昨天     │                     │ │ [发送]   │ │
│ └─────────────────────────┘                     │ └──────────┘ │
│ 空态：还没有保存的巡检，从右侧对话开始 →           │              │
├─────────────────────────────────────────────────┤              │
│ （旅程进行中：主区切换为 解析确认→草案→执行→报告）  │              │
└─────────────────────────────────────────────────┴──────────────┘
```

**关键决定：解析结果不放聊天气泡里。** 对话流里只留一行回执（"已识别：payment-api 配置变更巡检"），所有可选择、可操作的信息全部在主区渲染成结构化卡片——气泡是给人读的，主区是给人干的。

## ③ 旅程一：首访六屏（对话生成）

**屏 1 · 发起**：用户在对话框说"我要做一次 payment-api 巡检"。对话回执一行；主区从保存列表切换到"理解结果"。

**屏 2 · 解析确认（信息二次补充）**：主区标题"确认巡检信息"，三类可选卡片，全部默认勾选、可取消：
- 近期变更电子流（2 条 chip 卡：CHG-84501 调整超时 · 灰度 25%…）
- 关联服务与依赖（payment-api → settlement-db → invoice-worker）
- 可用信号（业务成功率 / p95 / 连接池 / Trace）
底部唯一主 CTA：`生成任务草案`。副文案一行："勾选本次要验证的范围"。

**屏 3 · 任务草案**：检查项列表（每项：名称 + 数据源 + 判定门禁一行），AI 高风险候选单独分区。唯一主 CTA：`确认并执行`（候选未处置时禁用——门禁继承）。

**屏 4 · 执行态**：步骤流 + 实时证据值，无口号。异常项红色内联。

**屏 5 · 报告**：行动结论大卡（唯一视觉高潮）→ **用户勾选项结果**分区（与屏 2 的选择一一对应，这是"报告包含用户刚选择的信息"的落点）→ **模型风险总结**分区 → 证据边界一行。

**屏 6 · 保存**：报告页底部安静的一条：
```text
── 这次巡检不错？────────────────────
[支付配置变更巡检____________] [保存]
保存后下次可从首页直接执行
```
命名输入框预填建议名（可改），保存后 toast 一行："已保存，下次从首页直接执行"。

## ④ 旅程二：复访直跑（绕过生成）

首页点`直跑` → **不经对话、不经草案确认**，但强制执行当前事实刷新：
- 顶部一行状态条："正在刷新当前事实…" → 结果徽标：事实一致（绿）/ 有差异（amber，列出差异 chips + `仍要执行`/`查看差异`）/ 重大漂移（红，禁止直跑，引导去对话框重新生成）。
- 通过后直接进入执行态 → 新报告。**每次直跑生成新的 InspectionRun**，历史报告从任务卡"上次报告"链接查看，不可改。

## ⑤ 复用与视觉规格

| 新元素 | 复用 |
|---|---|
| 保存任务卡 | `.prompt-card` 容器 + `.readiness` 状态胶囊 + 单主按钮纪律 |
| 对话框 | 右栏既有槽位；输入框圆角 16、聚焦 cyan 描边（现有 focus 规则） |
| 解析确认卡片组 | `.entity-cloud` chips + `.source-card` |
| 直跑事实条 | reconciliation 卡（`.reconciliation` 三态色） |
| 报告"勾选项结果"分区 | 现有报告双卡栅格 |
| 新增 token | **零**（沿用 DESIGN-SIMPLIFY 后的全部色值与字阶） |

**文案纪律抽查点**：对话框 placeholder 用示例句（"例如：巡检 payment-api 本周配置变更"），禁止"我是你的智能巡检助手"式自我介绍；保存成功只许一行 toast，不许弹庆祝卡。

## ⑥ 移动端（390px）

- 对话框降级为**底部固定输入条**（≥44px 命中区），对话记录上滑展开。
- 保存列表 = 首屏；直跑按钮全宽。
- 解析确认卡片单列堆叠；事实刷新条全宽横幅。
- 命名保存：底部抽屉，输入框 + 保存按钮堆叠。

## ⑦ 可验收 AC

- **AC-J1 首访全旅程**：对话输入 → 解析确认（可勾选/取消）→ 草案 → 执行 → 报告 → 命名保存，六屏可走通。
- **AC-J2 选择有回响**：屏 2 取消勾选的项，不出现在任务草案和报告里；勾选项与报告"勾选项结果"一一对应。
- **AC-J3 跨刷新持久**：保存后刷新页面，任务出现在首页"已保存巡检"（localStorage，界面标注本地 mock）。
- **AC-J4 直跑绕生成**：点直跑全程不触发自然语言解析与草案确认；产生新 InspectionRun（新 ID、新证据），历史实例不变。
- **AC-J5 漂移守门**：mock 重大漂移场景下直跑被禁，引导回对话；amber 差异需用户显式"仍要执行"。
- **AC-J6 文案纪律**：AC-S1 禁用词清单继续全部为零；新增界面不出现助手自我介绍、庆祝弹层。
- **AC-J7 移动端**：390px 两条旅程均可走通，无横向溢出，底部输入条不遮挡主 CTA。
- **AC-J8 空态**：无保存任务时首页显示一行空态引导，不显示假示例任务。
