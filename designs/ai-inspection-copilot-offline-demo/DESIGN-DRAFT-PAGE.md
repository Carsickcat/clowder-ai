# 草案页直观性改版（设计修订 · 终态）

触发：co-creator 反馈“任务草案的内容分布看不懂，建议更直观”。
设计诊断：不是文案问题，是**主次倒置**——需要用户行动的 AI 候选被压在下面，不需要行动的正式检查占满首屏。用户打开草案页的第一问是“要我干嘛？”，现版回答不了。

## 改版原则：行动优先，一屏一答

草案页只回答三个问题，按此顺序排布：

```text
Q1 要我确认什么？ → 待确认区（置顶，行动色）
Q2 系统会查什么？ → 执行清单区（次要，安静）
Q3 确认后干嘛？   → 底部主按钮（文案即后果）
```

## 具体改造

### 1. 顶部一行总结替代三个计数器

现状：“必查 4 / 建议 1 / 待确认 1”三个统计块（用户要自己做换算）。
改为一句话：

```text
本次将执行 4 项检查，另有 1 项 AI 建议需要你确认
```

数字自解释，零换算。无候选时显示“本次将执行 4 项检查，无需额外确认”。

### 2. 待确认区置顶并改名

- 区标题：“待确认项” → **“需要你确认”**（动词开头，直接说事）。
- 候选卡精简为三行：① 检查什么 ② 为什么建议查（AI 理由，保留“自己也不确定”的诚实表述）③ 两个按钮。
- 按钮文案改口语：`加查` / `不查`（现状“纳入计划/拒绝并留痕”是系统黑话）。留痕行为不变，只是不再拿机制名吓唬用户。
- 已处理的候选原地显示结果：“✓ 已加查” / “— 不查”，留在原位可改回。
- 指标 code 行折叠进“查看细节”。

### 3. 正式检查区降级并改名

- 区标题：“正式检查” → **“将执行的检查”**。
- 每项默认只显示一行：目的 + 对象（如“保护订单提交成功率 · order-api”），点开展开指标/门禁/失败动作/来源。
- 顺序按风险相关性排，高优先在前（沿用 priority 字段，不再显示“必/荐”角标——那是内部分类，不是用户语言）。

### 4. 主按钮文案说后果

- 有待确认未处理：`请先处理上方的建议项`（禁用态，文案指路而不是干禁用）。
- 全部就绪：`确认并开始巡检`。

### 5. 移动端

顺序不变：一行总结 → 需要你确认 → 将执行的检查（折叠）→ 底部主按钮。390px 单列天然适配。

## 不动的部分

候选处置门禁（高风险未处理禁确认）、六字段 Check Contract、留痕机制、五阶段流——行为零变化，纯呈现层改版。

## 验收 AC

- **AC-D1**：草案屏第一视觉区是“需要你确认”（有候选时）；无候选时第一屏直接是执行清单+主按钮。
- **AC-D2**：顶部一行总结，数字与实际清单一致；不出现“必查/建议/待确认”三个并列计数器。
- **AC-D3**：按钮文案为“加查/不查”；禁用态按钮文案指向待处理项。
- **AC-D4**：正式检查默认单行折叠，展开可见完整六字段。
- **AC-D5**：行为回归——候选门禁、留痕、阶段流转全部不变（现有测试应不红或仅快照更新）。
- **AC-D6**：390px 无横溢，主按钮不被底部输入条遮挡。
