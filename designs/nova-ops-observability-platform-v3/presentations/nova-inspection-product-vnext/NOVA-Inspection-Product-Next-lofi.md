# NOVA 智能巡检：产品功能与使用说明

> **受众**：业务负责人、运维负责人、发布负责人
> **案例**：`payments-router` / `production` / `v3.18.0` / `CHG-2481`
> **页面真相**：以当前 connected 的“左侧持久作业 + 右侧一屏 Case 工作区”为母版，不引入多级左树。
> **能力标识**：每页区分“当前已具备”与“AI 增强目标”；目标能力不冒充已上线。
> **AI 边界**：规则负责判定，AI 负责候选与解释，人负责发布与接受。

---

## P1：封面 — 不换页面骨架，只增强两段高认知成本工作

```text
┌─ NOVA · CONNECTED SANDBOX ─────────────────────────┐
│ 可复用巡检控制台                                    │
│ 左：持久作业      右：Revision / Case / Run / 报告 │
│                                                    │
│ AI 增强 ① 巡检项生成与编排                         │
│ AI 增强 ② 报告生成与解读                           │
└────────────────────────────────────────────────────┘
```

## P2：当前产品页面 — 为什么不做多级左树

```text
┌─ 当前实际页面 ─────────────────────────────────────┐
│ [持久作业] │ [创建 revision] [新建 Case]           │
│ [作业表单] │ [执行阶段 ▼] [执行只读巡检]           │
│            │ [AUTHORITATIVE RUN] [不可变报告]      │
└────────────────────────────────────────────────────┘
```

- 一次使用围绕一个作业和一个 Case 推进，阶段需要同屏可见。
- 左侧是上下文选择和保存表单，不是产品功能菜单。
- 规模增长时用搜索、筛选和折叠；不在 Case 内塞一棵导航树。

## P3：当前用户怎么用 — 已上线闭环

```text
保存作业与 revision 1 → 新建独立 Case → 选择执行阶段
→ 执行只读巡检 → 查看服务端权威 Run
→ 记录人工接受并固化报告
```

当前 connected：单巡检项、手工填写 query/threshold、没有 connected CLAW。
AI 增强目标：多巡检项生成/编排与证据化报告解读，嵌入同一工作区。

## P4：为什么需要 AI — 规则系统做不了的不是判定，而是语义劳动

```text
没有 AI：人手工读依赖图/SLO/runbook/变更说明/历史事故
         → 手工翻译成检查项 → 手工关联多阶段结果 → 手写报告

有 AI：  归并异构上下文 → 生成有理由的候选 → 标出覆盖缺口
         → 汇总确定性证据 → 解释风险 → 草拟治理建议
```

规则仍负责查询、计算、阈值和 PASS/WARN/FAIL；AI 不接管权威。

## P5：AI 能力一（输入）— 先建立巡检上下文包

```text
服务档案 + 单跳依赖快照 + SLO/指标目录 + runbook
        + 变更说明 + 历史事故/历史 Case
                     ↓
     Inspection Context Pack（来源、时效、scope、omissions）
```

AI 的价值是跨结构化与非结构化资料做语义对齐；缺失资料必须显式暴露。

## P6：AI 能力一（输出）— 候选巡检项不是一串指标名

每个候选项必须包含：检查对象、阶段、查询草稿、阈值依据、生成理由、依赖路径、证据来源、置信度、覆盖缺口。
候选只进入草稿，不直接执行。

## P7：在当前工作区编排 — 不新增左树

```text
左：持久作业                         右：创建 revision 2
                                     [AI 候选 6] [已选 4]
                                     变更前：成功率 / 延迟
                                     灰度：错误率 / 下游依赖
                                     [+添加] [编辑] [删除]
                                     [保存 revision 2]
```

发布后 Revision 不可变；Case 绑定自己的新鲜快照与 baseline。

## P8：同一屏执行阶段 — 当前交互继续保留

阶段下拉、执行按钮、Case rail、权威 Run、证据来源与报告都保留在同一 workspace。
AI 不推进阶段；UNKNOWN、过期或连接失败继续 fail-closed。

## P9：AI 能力二（报告生成）— 先固化事实，再生成文字

```text
Run/CheckResult/Evidence/Comparison（确定性）
                    ↓ 只读引用
事实摘要 → 异常关联 → 风险解释 → 治理建议 → 不确定性
                    ↓
带证据引用的解释层（不能改 verdict）
```

## P10：用户看到的报告 — 每个判断都能点回证据

报告首屏回答：发生了什么、影响哪些依赖、为什么重要、建议先做什么、还有哪些未知。
每句话引用 runId/checkId/queryDigest/window；AI 推断与确定性事实分栏呈现。

## P11：CLAW 怎么用 — 作为同屏助手，不是新入口

```text
“为什么建议检查 checkout-api？” → 返回依赖路径与来源
“灰度报告最重要的风险是什么？” → 返回证据化摘要与不确定性
“把建议加入草稿” → 页面展示 diff，用户确认后保存 Revision
```

当前页面没有 connected CLAW；这页明确标记为 AI 增强目标。

## P12：产品能力全景 — 当前基座 + 两个 AI 增强环节

```text
当前基座：Job → Revision → Case → Run → Decision → Report

AI 增强 A：上下文 → 候选巡检项 → 编排草稿
AI 增强 B：权威证据 → 解释 → 风险与治理建议

规则负责判定 · AI 负责候选与解释 · 人负责发布与接受
```

## HTML 制作合同

- 单文件、内联 CSS/JS、无外链；键盘、触摸、全屏、打印、390px 手机可用。
- 真实页面标签与 `InspectionOperationsPage.tsx` 同源。
- 页面示意使用两列控制台，不出现 `.side-nav` / `.nav-item` 多级导航结构。
- “当前已具备”和“AI 增强目标”必须首屏可辨；当前能力不含 connected CLAW。
- AI 页必须同时说明输入、产物、用户动作、确定性边界与失败状态。
