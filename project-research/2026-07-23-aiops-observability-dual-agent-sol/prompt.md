# 2026 AI 运维双 Agent 可观测平台竞品研究

## 1. Problem Frame

我们正在规划一套从传统云服务运维监控平台向“数据科学 + 智能运维平台”演进的 2026 产品。平台已有监控、告警、日志、巡检、拨测和 AI 告警诊断，不重建数据采集面。

本研究只回答两个待建 Agent 应如何成为真实可运行、可观察、可治理的产品：

- **故障诊断 Agent**：从异常入口持续组织影响、时间线、证据、假设、结论与处置。
- **智能巡检 Agent**：高频评估业务健康并生成报告与风险提示；支持保障、大促、变更；支持 NL2Inspection 创建、验证、执行和治理巡检项。

最终需要形成能约束产品方案和高保真设计的证据，而不是竞品功能罗列或 AI 营销话术。旧版“能力介绍首页 + 同构模块页签”已经被否定，不作为设计基线。

## 2. Hypotheses

1. 领先产品的核心不是聊天框，而是持久化的运行对象：Problem / Investigation / Mission / Guardian / Run / Finding / Evidence / Action。
2. 两个 Agent 应共享服务、拓扑、变更、信号和证据上下文，但保持不同触发、状态机和成功标准。
3. 高频巡检的可靠价值首先来自持续健康评估、异常发现和覆盖治理；通用“风险预测”需要数据、基线、可比性和置信度门禁，不能默认承诺。
4. NL2Inspection 的成熟形态不是自由文本直接执行，而是“意图解析 → 结构化检查草案 → 数据/权限/成本验证 → 回放 → 人工发布 → 版本化运行”。
5. 真正可用的高保真必须呈现正在运行的系统：实时健康、任务状态、风险门禁、证据、新鲜度、覆盖率、人工决策和闭环结果，而不是讲解能力。

## 3. Disconfirm First

优先寻找能反驳或限制上述假设的证据：

- 厂商是否真的提供持久调查/巡检运行对象，还是仅有对话摘要？
- 所谓预测是确定性预测、异常检测、趋势外推还是营销措辞？是否披露输入窗口、置信度和适用边界？
- NL 是否能生成并执行检查？是否需要批准、模板、权限或 Preview/实验状态？
- AI 结论是否可回溯到查询和证据？是否支持 inconclusive / unknown / revision？
- 自动处置是否默认开启？权限、审批、审计、回滚如何约束？
- 保障、大促、变更的工作流是否为正式产品对象，还是只能用通用 Dashboard 拼装？

## 4. Source Mix

只使用可核验的一手资料作为产品事实：

- Alibaba Cloud：CloudMonitor、ARMS、SLS、CloudOps/相关智能运维与巡检官方文档。
- Dynatrace：Davis AI、Problems、Site Reliability Guardian、Workflows/Automation 官方文档。
- Datadog：Bits AI SRE、Watchdog、Incident/Investigation、Workflow Automation、Synthetics 官方文档。
- Google Cloud：Gemini Cloud Assist investigations、Cloud Monitoring、SLO、Synthetic Monitoring 官方文档。
- 必要时补充 AWS/Azure 等一手资料作为反例或边界参照，但不扩成泛化竞品大全。

来源记录必须包含 URL、标题、访问日期、产品状态（GA/Preview/未说明）和“事实/推断”区分。搜索结果摘要只能作为线索，不能作为证据。

## 5. Local Constraints

- 现有数据面：日志、告警、指标、巡检、拨测、服务/资源关系、变更，以及既有 AI 告警诊断。
- 不重建监控平台，不以自由 Prompt 直接执行生产变更，不展示模型隐式推理链。
- 规则/基线负责可测试判定；AI 负责候选生成、跨源关联、证据缺口、解释和报告编排。
- 任何正向健康结论都受 coverage、freshness、baseline comparability、permission/cost 等门禁约束；`unknown` 不得折算为 healthy。
- 高保真要覆盖桌面主工作面与手机决策/跟进体验，但不把手机当完整分析终端。

## 6. Output Schema

### A. Evidence ledger

逐条记录：厂商、能力、真实运行对象、触发入口、核心交互、持久状态、AI 作用、人工/规则边界、产品成熟度、来源、可迁移启示。

### B. Comparative synthesis

按以下维度对比，而非按厂商写宣传摘要：

1. 诊断入口与调查对象。
2. 高频健康评估与保障/变更运行对象。
3. NL 创建检查/查询的编辑—验证—发布链。
4. 证据可追溯、未知/不确定状态与修订。
5. 自动化、权限、审批和审计边界。
6. 用户在页面中实际做出的业务决策。

### C. Product proposal contract

- 原子能力与领域对象。
- 两个 Agent 的状态机、协作协议和越权边界。
- 保障、大促、变更、日巡、故障诊断、NL2Inspection 的用户旅程。
- 页面清单及每页的角色、触发、决策、数据、AI 增益、状态变化。
- 一期/二期边界、产品指标和风险门禁。

### D. High-fidelity design handoff

- 信息架构、页面布局、关键组件、状态、交互、Mock 数据和验收路径。
- 每个工作面必须有不同的任务和数据密度；不得复制同一套卡片。
- 明确哪些内容是实时运行态、历史报告、AI 建议、人工确认和不可判定状态。

## 7. Decision Interface

研究最终必须支持以下决策：

1. 2026 一期先打穿哪个完整场景，为什么？
2. “高频巡检”“风险预测”“NL2Inspection”各自应承诺到什么成熟度？
3. 首页的首要对象是什么：服务健康、保障任务、事件队列还是 Agent 活动？
4. 两个 Agent 何时协作、何时必须保持隔离？
5. 哪些交互必须由规则/人确认，哪些可由 Agent 自动进行？
6. 高保真如何证明这是可用运维系统，而不是能力官网？

## 8. Risk Register

- 把异常检测包装成可靠风险预测。
- 把无数据、数据过期、覆盖缺失或基线漂移显示为绿色。
- 两个 Agent 争抢同一事件或重复生成结论，形成状态分裂。
- NL 生成的检查语义正确但数据源、时间窗、权限或成本不可执行。
- 用模型解释替代证据链、规则判定和人工责任。
- 五个传统模块被统一工作台吞掉专业入口，或再次退化为同构页签。
- 只展示 Agent 输出，不展示其正在运行、等待、受阻、重试、修订和被人工否决的状态。
- 竞品 Preview 能力被误当作稳定 GA 基线。
