# 从 AI 运维全景到“巡检健康中枢”

研究日期：2026-07-20
适用前提：大型企业已有日志、告警、指标、巡检、拨测和部分 AI 告警诊断能力；本方案不重建事实数据面，也不把 LLM 直接接入生产写操作。

## 结论先行

下半年不应做一个“AI 帮你写巡检报告”的孤立功能，而应做一个以**业务/服务健康单元**为中心的主动健康治理闭环：

> **定义检查 → 触发执行 → 证据化发现 → AI 解释 → 责任人整改 → 复验 → 面向不同人群的报告/分享。**

AI 的位置很明确：

- **替人拼装、解释、归纳和发现覆盖缺口**；
- **不替代确定性判定、权限系统和责任人决策**；
- 所有 AI 结论都必须区分“事实 / 推断 / 建议”，并回链到数据、时间窗与检查定义。

这比“指标大盘 + 一段 AI 摘要”多了一层关键能力：大盘能回答 **“系统健康到什么程度、为什么、谁要在什么时候做什么，以及做完后是否真的变好了？”**

### 对“效率提升”的严谨结论

公开资料足以证明：行业正在把跨系统取证、假设组织、报告/交接和定时健康检查产品化。它们**不足以证明一个可跨企业复现的 MTTR 或人力降幅**。例如，腾讯云数据库 AI 服务披露的“CPU 诊断 30 分钟到 2 分钟”是特定 MySQL/DBA 产品页的数字，未公开方法论，不能作为通用目标。[证据审计](evidence-ledger.md)

所以产品要承诺的是可测的工作流改善：更快形成可验证健康结论、更少手工跨系统拼接、更高覆盖和更短整改闭环；实际 MTTR、成本和人效由本团队做对照试点后再宣称。

## 2. 产品定位：巡检大盘不是“看板”，而是健康治理中枢

### 2.1 一条必须闭环的数据链

```text
业务 / 服务健康单元
  └─ 资产、拓扑、SLO、Owner、重要性、环境、近期变更
          │
          ▼
检查定义 CheckDefinition ──► 巡检计划 Plan（定时 / 变更触发 / 手动 / 保障期）
          │                                 │
          │                                 ▼
          └──────────────────────────► 执行 Run（不可变快照）
                                             │
                                             ▼
                                    证据 Evidence → 发现 Finding
                                             │             │
                       AI 解读（事实/推断/建议）             ▼
                                             └──► 整改 Action → 复验 Verification
                                                                      │
                                                                      ▼
                                                         报告 / 分享 / 复盘 / 规则改进
```

这是核心架构判断：**“报告”是从 Run、Finding、Action、Verification 投影出来的视图，不能反过来成为事实源。**

### 2.2 六条产品原则

1. **以健康单元而非资源为中心**：健康单元可以是业务系统、应用、服务、关键链路、集群或数据库域；它要挂载 owner、业务等级、依赖、SLO、巡检包和风险承受度。
2. **分开事实、推断和动作**：确定性检查结果与原始证据是事实；AI 对根因/风险的解释是推断；工单、Runbook、升级建议是动作。界面与 API 都不允许把三者混成一句话。
3. **检查定义可声明、可版本化、可回放**：运行的不是一段 prompt，而是有 schema、数据源、范围、时间窗、阈值/基线、证据要求、严重度、成本上限、预期输出和测试样本的定义。
4. **评分只做导航，不做遮羞布**：健康分可帮助排序，但最高风险 blocker、覆盖缺口、数据缺失和过期整改必须独立显著展示；不能用“82 分”掩盖核心服务不可用。
5. **报告随角色而变，事实不随角色而变**：同一次巡检可生成高管一页纸、服务 owner 待办版、SRE 证据版、审计归档版；它们共享同一 Run/Findings ID。
6. **AI 只读、最小权限、完整审计**：数据/工具按健康单元和岗位授权，敏感字段脱敏；任何运行的模型、上下文摘要、工具调用、报告版本和人工 feedback 都可追溯。

## 3. 先做哪几类业务场景

| 优先级 | 场景 | 为什么最适合第一批 | 应有体验 | 成功标准 |
|---|---|---|---|---|
| P0 | **发布后健康验证** | 有明确变更、时间窗、owner 和期望结果，最容易判断“巡检是否有用” | 发版后 5–15 分钟与次日自动运行；展示变更前后差异、SLO、错误、资源、拨测与依赖异常；未通过自动建待复验项 | 更快发现发布回归；证据完整；误报可控 |
| P0 | **关键服务日巡 / 夜间巡** | 高频、重复、人工整理成本高，适合先把现有巡检结果变成闭环 | 每日风险清单、昨日新增/消失问题、逾期整改、数据缺失；只在有变化或高风险时打扰人 | 报告编辑/拼接下降，整改闭环时间下降 |
| P1 | **大促/保障前健康评估** | 跨可靠性、容量、配置、安全、拨测与预案，价值易被业务感知 | 以业务架构/链路为范围，给“阻断项 / 需决策项 / 观察项”，并关联负责人、SLA、预案与复验 | 关键检查覆盖率、阻断项闭环率、保障期间漏检率 |
| P1 | **容量与成本健康治理** | 现有指标和资源数据一般较成熟，适合定期给出风险/优化任务 | 风险趋势、阈值临界、低利用率、预算变化，AI 解释业务影响和证据 | 任务采纳率、回收/扩容后复验通过率 |
| P2 | **从事故/变更复盘生成候选检查** | 能把团队经验产品化，但准确性、数据可用性和成本要先验证 | 从历史事故提炼“应有检查”，输出候选 DSL、证据、覆盖范围、反例和回放结果 | 候选被人工采纳并在回放中有效 |

**我的取舍**：先用“发布后健康验证 + 关键服务日巡”打穿闭环；不要一开始上全公司通用智能巡检，也不要先花半年做大而全的健康分。

## 4. 巡检大盘的产品能力与用户交互

### 4.1 四个页面，不是一个超级屏

| 页面 | 主要用户 | 用户第一问 | 关键组件 |
|---|---|---|---|
| **健康总览** | 服务 owner、值班、负责人 | “哪里需要我现在关注？” | 业务健康单元树；P0 blocker；风险趋势；覆盖缺口；逾期整改；近期变更影响；一键进入本次 Run |
| **巡检中心** | 值班 / SRE | “这轮巡检查了什么、发现了什么、可信度如何？” | Run 时间线；检查包状态；Finding 列表；事实/推断/建议三栏；原始日志/指标/Trace/拨测深链；历史对比 |
| **检查工作室** | 平台/SRE/领域专家 | “怎样把经验变成可靠检查？” | 模板库、AI 候选项、DSL 编辑、数据可用性/成本预估、历史回放、灰度、版本与审批 |
| **治理与报告中心** | 负责人、高管、审计 | “风险是否被治理、我应如何分享？” | 整改看板、Owner/SLA、复验状态、角色化报告、脱敏/权限受控的分享链接、反馈与规则改进 |

### 4.2 健康总览的核心布局

1. **顶部不是总分，而是行动摘要**：`3 个阻断项 · 7 个高风险项 · 18 个待复验 · 2 个关键服务无足够数据`。
2. **左侧是业务/服务树**：按业务域 → 应用 → 服务/链路 → 环境钻取；同时显示 owner、等级和覆盖率。
3. **中间是风险与变化**：按“新增、恶化、长期未解、即将过 SLA、变更相关、数据缺失”排序，而不是按资源数量排序。
4. **右侧是 AI 健康简报**：每一段都有 `证据`、`为什么现在值得关注`、`未知/反证`、`建议下一步` 四个可展开区块。
5. **底部是整改与复验队列**：状态流为 `new → acknowledged → in progress → pending verification → verified / waived`；“waived”必须有期限、理由与审批人。

### 4.3 三条关键交互路径

**A. 从变化进入巡检（发布后验证）**

发版事件或配置变更出现 → 系统按服务/环境匹配检查包 → 延迟窗口后执行 → 展示“变更前基线 / 变更后证据 / 可疑差异” → 人确认或驳回 Finding → 自动生成整改和次日复验。
这是优先于纯 cron 的入口，因为它天然给了 AI 正确的范围、时间和对照组。

**B. 从巡检结果进入行动**

点开 Finding → 先看到确定性结果和证据 → 再读 AI 的解释与置信度 → 选择“创建整改 / 关联已有问题 / 标记非问题 / 请求补证据” → 由系统安排同一检查或验证检查复跑。
借鉴 AWS 的“接受/丢弃 observation”机制：人类反馈应反馈到具体 Finding，而不是只有一个模糊的点赞。[AWS](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/Investigations.html)

**C. 从自然语言生成检查，但不直接上线**

用户输入：“帮我为支付链路生成一套发版后 30 分钟健康检查”。AI 输出的是**候选检查包**，而不是一个立即生效的 prompt：

| 必填字段 | 例子 |
|---|---|
| 目标/适用范围 | 支付服务生产环境，关联订单、网关、DB、拨测链路 |
| 触发与窗口 | 发布完成后 10 分钟、30 分钟、次日各一次 |
| 信号与判定 | SLO、错误率、P95、资源饱和、关键日志模式、拨测、近端变更 |
| 证据契约 | 每个失败项的查询链接、样本、时间窗、基线与数据质量说明 |
| 风险/严重度 | blocker / high / medium；业务等级如何影响排序 |
| 动作与复验 | 关联 Runbook/负责人、预期修复后复验条件 |
| 验收测试 | 历史 30 天回放、已知故障样本、无数据/噪声反例、查询成本预估 |

只有通过 `schema 校验 → 数据源权限校验 → 静态/成本校验 → 历史回放 → 人工审批 → 灰度`，检查包才可启用。K8sGPT 的 analyzer 先行模式支持这种分层：**规则/模型负责判定，LLM 负责生成和解释。**[K8sGPT](https://github.com/k8sgpt-ai/k8sgpt)

## 5. AI 能力分层：哪些该做、哪些先不做

| 能力 | 产品形态 | 判定 | 原因与门槛 |
|---|---|---|---|
| 报告草稿与多角色改写 | 同一 Evidence/Findings 生成高管、owner、审计三个视图 | **采纳** | 风险低、立即省去整理时间；但禁止编造结论，须显示引证和未知项 |
| 巡检报告问答/解读 | “本周为什么支付域变差？”“哪些项是发布相关？” | **采纳** | 只读证据范围内的问答；需要范围可见、查询轨迹和引用 |
| 巡检项候选生成 | 目标 → 检查 DSL/模板 + 回放样例 | **试点** | 高价值但质量波动大；必须走校验/审批/灰度链 |
| 检查覆盖缺口发现 | 比对服务等级、依赖、事故、已有检查，提示缺少的维度 | **试点** | AI 擅长召回和归纳；结果必须是“候选缺口”，由专家确认 |
| 语义型巡检 | 读配置、Runbook、变更说明、日报，判断是否存在非结构化风险 | **试点** | 可补规则盲区，但只可产生 Finding 候选，不能独立拦截生产 |
| 变更风险预测 / 自动扩展检查范围 | 结合历史变更、依赖图、近期事故推荐检查包 | **试点** | 先限定在高价值服务和只读数据，验收回放的 Precision/Recall |
| 自由文本自动修复 | AI 自选命令、改配置、重启/扩缩容 | **搁置** | 与巡检价值无关且风险极高；若未来需要，只能执行人工批准的版本化 Runbook |

## 6. 效率与质量：不要用“AI 很聪明”验收

### 6.1 首期北极星指标

| 目标 | 指标 | 解释 |
|---|---|---|
| 更快形成结论 | **TTHC**（Time to Health Conclusion） | 从触发到出现“带证据、可行动、有人确认”的健康结论所需时间 |
| 少做手工拼装 | 每 Run 的跨系统跳转/手工导出次数、报告人工编辑分钟数 | 能直接反映巡检、报表和汇总环节的摩擦 |
| 更全的覆盖 | 关键健康单元的检查覆盖率、数据完整率、变更后验证覆盖率 | 防止 AI 只优化已有强信号区域 |
| 更有效的治理 | Finding 的确认率、整改按 SLA 完成率、复验通过率、重复发现率 | 关注实际闭环而不是报告产量 |
| 更安全可信 | 无证据结论率、严重误报/漏报抽检率、越权/敏感数据事件、AI 引用点击率 | 效率不能抵消安全和可解释性失败 |
| 成本可控 | 每 Run 的模型/查询成本、空跑比例、单位有效 Finding 成本 | 定时巡检频率越高，必须越明确地管理成本 |

### 6.2 试点评估方法

选两个业务重要、信号成熟、故障类型相对重复的服务，保留同一批既有巡检作为 baseline：

1. 前两周只上线**证据化报告 + 整改/复验闭环**，不改变判定逻辑；
2. 再以交错时段或相似服务对照启用 AI 报告解读和候选检查生成；
3. 由未参与生成的人盲评 30–50 份报告：证据完整、事实正确、建议可执行、是否遗漏关键风险；
4. 用历史事故和发布回归回放新检查包；记录 Precision、遗漏、成本和人工 verdict；
5. 只有在“无 P0 安全/越权、证据完整率达标、TTHC 改善、误报可接受”同时满足时，再扩大范围。

借鉴 AIOpsLab 的不是其微服务环境，而是**任务—输入—轨迹—评估器**的验收思想。[AIOpsLab](https://github.com/microsoft/AIOpsLab)

## 7. 90 天落地路线

### 0–30 天：把既有巡检变成可治理的证据工件

- 定义 `HealthUnit / CheckDefinition / Plan / Run / Evidence / Finding / Action / Verification / Report` 九个对象及 ID 链路。
- 选择 2 个服务、3 个检查包（发布后、日巡、保障前）接入现有日志/指标/告警/拨测。
- 上线健康总览、巡检 Run 详情、Finding→整改→复验状态机，以及基于事实模板的报告生成。
- 设定数据最小化、角色权限、报告脱敏/分享、模型和查询成本上限。

### 31–60 天：让 AI 参与解释与检查创作，但只能在沙箱中生效

- 上线“事实 / 推断 / 建议”三栏的 AI 解读、跨报告问答和多角色报告。
- 上线检查工作室：自然语言到候选 DSL、数据可用性验证、历史回放、成本预估、人工审批和灰度。
- 建立反馈闭环：对每条 AI Finding/建议进行采纳、驳回、补证据、关联问题的结构化反馈。

### 61–90 天：从单次巡检扩到主动健康治理

- 增加变更触发、保障期和容量治理三种 Plan；优先“发版后 10 分钟 + 次日复验”的模式。
- 用服务依赖、事故/变更历史和检查覆盖，生成“缺什么检查”的候选清单。
- 建立月度回放集和上线门禁；模型、Prompt、连接器或检查定义升级均重新评估。

### 不做清单

- 不把健康分作为唯一管理结论；
- 不给 AI 写生产权限；
- 不把自由 prompt 当巡检定义；
- 不以厂商 ROI 数字替代本团队基线；
- 不在没有数据质量、owner 和复验能力的业务线强推智能巡检。

---

## 最终建议

如果我是这套产品的负责人，我会把名字定成 **“巡检健康中枢”**，一期不是“AI 生成报告”，而是一个窄而完整的承诺：

> **关键服务每次发版后和每天都能得到一份可回证、可解释、有人负责、能复验的健康结论。**

这条承诺一旦跑通，巡检项生成、AI 解读、分享报告、容量治理和大促保障都会成为同一条健康治理链上的自然扩展；反过来，如果没有这条链，再漂亮的 AI 报告也只是一层容易被忽略的文案。
