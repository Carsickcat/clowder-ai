# 变更全生命周期巡检产品调研 Prompt

## Problem Frame

为 NOVA Ops 设计一个可实际操作的巡检纵切，覆盖变更前准入、灰度期间持续验证、变更后对比验收。目标不是扩展“大而全”菜单，而是回答用户如何从一句自然语言请求开始，经过计划确认、执行、风险判断和报告解读，完成一次可追溯的变更巡检。

非目标：AI 自主执行生产变更；自由 Prompt 直接发布生产巡检；脱离证据给出健康结论；重新设计故障、保障、治理等其他模块。

## Current Hypotheses

1. 核心长生命周期对象应是一次变更巡检任务，而不是页面菜单。
2. 对话负责表达意图、补齐范围和动态调整；页面负责审阅计划、观察执行、比较证据和做人工决策。
3. 变更前、变更中、变更后应复用同一检查计划，但产生不可变的独立 Run 与 Report。
4. 结论至少包含通过、风险、不可判定三态；数据新鲜度、覆盖率和基线可比性可以阻断准入。

证据缺口：竞品如何建模计划、运行、基线、灰度对照和报告；对话与页面之间如何切换；哪些能力是真正产品化而非营销描述。

## Disconfirm First

- 查找“聊天即可完成全部巡检、无需计划确认”的成熟反例。
- 查找不保存前置基线仍能可靠判断变更影响的成熟反例。
- 查找将变更前、中、后拆成无关联任务反而更可用的反例。
- 查找强制单一三态结论会掩盖局部目标差异的反例。

## Source Mix Quota

- 只使用厂商官方文档、官方产品说明或官方开源文档作为事实来源。
- 至少覆盖：长期任务/自然语言编排、发布门禁/灰度验证、前后对比、运行报告与人工介入。
- 搜索候选：Alibaba Cloud STAROps、Dynatrace Site Reliability Guardian、Harness Continuous Verification、Keptn、Google Cloud Assist/Synthetic Monitoring、Datadog Bits Investigation。

## Local Constraints

- 本地原型使用 React 19、纯前端领域 reducer 和 mock 数据。
- 用户界面以中文为主；英文只保留系统 ID、指标名和查询语句。
- 必须允许页面点击和 Claw 对话驱动同一状态机。
- 每个页面只突出一个当前任务和一个主要动作。
- 不触碰生产数据，不部署公网，不修改运行时配置。

## Output Schema

对每个竞品输出：

1. 可确认的对象模型与触发方式。
2. 用户交互路径。
3. 变更前、变更中、变更后分别覆盖什么。
4. 基线、门禁、不可判定、报告和人工介入的处理。
5. 对 NOVA 可直接采用、需要验证、明确不采用的部分。
6. 置信度与官方来源。

## Decision Interface

- 采用：能直接映射到本期状态对象和用户旅程。
- 试点：需要真实数据或后端能力，本地只展示边界。
- 搁置：超出巡检纵切或容易制造虚假自动化。
- 否决：与可审阅、可追溯、人在环边界冲突。

## Risk Register

- 把自然语言生成误写成“直接发布”会造成生产风险。
- 只展示结论不展示覆盖率、基线和证据会制造虚假确定性。
- 用多个页面映射技术模块会再次破坏用户旅程。
- mock 运行若没有明确标识，可能被误认为真实生产能力。
